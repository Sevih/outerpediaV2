# Equipment Detail — Console redesign + interactive configurator

Recap of the equipment **detail page** (`/equipment/[slug]`) redesign and the
interactive "live build" preview. Written to hand off to Claude later.

## TL;DR

- The detail page was redesigned in the **"Console" direction** (came from a Claude
  Design handoff): a HUD hero bar + bracketed `[ MODULE ]` 2-column grid. Accent is
  **rarity-driven** (real gear has no element).
- A second **interactive preview** lets the user drive a live build (enhancement /
  breakthrough / reforge / Singularity Ascension) and watch main stats, substats and
  passives recompute. It is **gated behind `?build=live`** (client-only flag) — the
  production default is the static Console view, untouched.
- The live view is wired to **real data** (`data/equipment/item-stats-detail.json`)
  through the data layer; formulas live in a pure client-safe util.

## Files

| File | Role |
|------|------|
| `src/app/[lang]/equipment/[slug]/page.tsx` | Server component. Fetches `liveDetail` via `getItemLiveDetail(equipment)` and passes it as a prop. |
| `src/app/[lang]/equipment/[slug]/EquipmentDetailClient.tsx` | Default static **Console** view (production). Reads `?build=live` client-side (in `useEffect`, no SSR/SEO impact) and swaps to the interactive inner when set. |
| `src/app/[lang]/equipment/[slug]/EquipmentDetailInteractive.tsx` | The interactive preview (`EquipmentInteractiveInner`). Slider/tabs/Ascend controls + live modules + the data adapter `buildSpec`/`buildModel`. |
| `src/app/[lang]/equipment/[slug]/equipment-console-shared.tsx` | Shared Console primitives used by both views: `Module`, color tokens, `CharacterRefCard`, `AscensionContent`/`AscensionContentForSet`, stat/effect content, `ASCENSION_LABELS`, etc. Single source of truth (avoids a circular import). |
| `src/lib/data/item-stats-detail.ts` | Data layer. Loads `item-stats-detail.json` (cached) and resolves a serializable `ItemLiveBundle` per item (NOT EE). |
| `src/lib/equipment-formula.ts` | Pure, client-safe progression math + serializable types. No fs/JSON access. |

`?build=live` is the only entry point to the interactive view, e.g.
`https://outerpedia.local/equipment/surefire-greatsword?build=live`.

## Data source — `data/equipment/item-stats-detail.json`

Generated by `scripts/generate-item-stats-detail.py` (do not edit by hand). Covers
**weapons, accessories, talismans, armor** — **NOT EE**. Keyed by `ItemTemplet` id.

- `getItemLiveDetail(equipment)` maps:
  - weapon / accessory / talisman → `items.{weapons,accessories,talismans}[equipment.data.id]`
  - armor **set** → `equipment.data.id` is the `SetOptionID` → `sets[id]` + the four
    armor pieces filtered by `setId` (legendary 6★, one per slot).
  - EE → returns `null` (no datamine detail) → live view falls back to `eeStatRange`
    + the curated effect (`effect`/`effect10` by level).
- Returns `ItemLiveBundle = { meta, item }` (serializable, safe to pass to the client).
  `meta` carries `constants`, `percentStats`, and a `statPercent` map.

`level` field on the curated equipment = **star count** (5 or 6). Used as the reforge base.

## Progression mechanics (as implemented)

Three independent controls drive everything; main / effect / substats are decoupled:

| Control | Range | Drives |
|---------|-------|--------|
| **Enhancement** | +0 → +10 (→ +15 if ascended) | main stat(s) |
| **Breakthrough** | T0 → T4 | main stat(s) **and** the passive / set-effect text |
| **Reforge** | 0 → N (N = stars; → stars + reforgeBonus once ascended) | secondary stats only (link TBD, see below) |

### Formulas (`src/lib/equipment-formula.ts`, mirrors `formula.*` in the JSON)

```
floorDisplay(v, key) = percentStats.has(key) ? floor(v*10)/10 : floor(v)   // EFF/RES round to int but DISPLAY as %
mainStat(base, key, lv, tier)      = floorDisplay(base * (1 + 0.4*lv) * (1 + 0.05*tier), key)   // lv 0..10
mainStatAscended(base, key, lv, t) = floorDisplay(base * mult * (1 + 0.05*t), key)              // lv 10..15
   mult = 1 + 0.4*10 + activation(0.15) + sum(steps[0 .. lv-10])   steps = [.1,.1,.1,.1,.2]
talismanStat(levels, lv) = levels[lv]                                  // no breakthrough, lookup table
subValue(step, segments, key) = floorDisplay(step * segments, key)     // substat = step × n segments
```

- `mainAt(base,key,lv,tier, ascended)` dispatches: `ascended && lv >= 10` → ascended
  table, else standard. So a **non-ascended +10 = standard 5.00**, an **ascended +10 =
  5.15** (the +3%). Multipliers: +10 ascended 5.15 → +15 5.75 (= +15% over standard +10).
- `% display` uses `statPercent` (statMeta) — note EFF/RES are **not** in `percentStats`
  (so their mains floor to an integer) but **are** percent for display.

### Mains — "Main Stat" vs "Possible Main Stats"

`item.mainStats` is a list of slots, each `fixed` or `choice`:

- **fixed** slot → an actual **Main Stat**, always present (e.g. weapon ATK flat; armor
  fixed mains). Rendered in the `[ MAIN STAT ]` module.
- **choice** slot → **Possible Main Stats** (one is rolled at drop). The UI shows **all
  options with their live value** and lets the user **select** one. Rendered in the
  `[ POSSIBLE MAIN STATS ]` module.
- Weapon = ATK fixed + one % choice. Accessory = one choice. Talisman = one choice with
  per-level `levels[]`. Armor = fixed mains per piece (no choice).

### Substats — "Possible Substats"

- Pool comes from `subStatPools[subStatGroupId]` (step, max, `maxSegmentsPerStat`).
- **Effective pool** excludes the **fixed mains** (`excludedSubStats`) **and the selected
  choice-main** (a stat can't be both main and sub). The other, non-selected possible
  mains stay available as substats.
- The UI shows **all** possible substats as a value range `+min ~ +max` (1 segment →
  max segments). **Reforge → substat-value linkage is intentionally deferred** ("on verra
  plus tard"); the reforge slider currently doesn't drive substat values.

### Passives / set effects (multilingual token templates)

- Weapon / accessory `passive`: `{ name: LangMap, desc: LangMap, valuesByTier: Record<token,value>[] }`.
  `renderPassive(p, lang, tier)` picks `desc[lang]` and substitutes the per-tier tokens
  (values already formatted, wrapped in `<color=#28d9ed>` by the renderer). The module
  title = the passive name; `GameText` parses `<color=#hex>` tags + newlines.
- Armor set passive lives in `sets[setId]`: `2pc` / `4pc`, each `{ base: LangMap, bt4: LangMap }`.
  `renderSetEffect(blk, lang, tier)` → `base` for T0..T3, `bt4` from T4.
- Talisman / EE keep their **curated** effect (`effect_desc1`/`effect_desc4`, or EE
  `effect`/`effect10`), shown via `formatEffectText`, stepped by level.

### Singularity Ascension (explicit button)

- `constants.singularity`: `activation 0.15`, `steps [.1,.1,.1,.1,.2]`, `reforgeBonus 3`,
  eligibility `minRarity legendary` / `minStar 6` / `slots`, + a `note`.
- Ascension does **not** consume an enhance level — the gear stays +10 but the multiplier
  jumps 5.00 → 5.15, unlocks +11..+15, and grants **+3 reforge attempts**.
- **Prerequisites**: legendary 6★ (`canAscend`) **at +10** with **reforge at base max
  (e.g. 6/6)**.
- The UI exposes an explicit **`✦ Ascend` button** (in the CONFIGURE bar), enabled only
  when the prereqs are met. Clicking ascends → enhancement extends to +15, reforge to
  `stars + reforgeBonus` (9), main uses the ascended table, accents turn **fuchsia**.
  The button toggles back to **`✦ Ascended`** to de-ascend (clamps enh → +10, reforge →
  base) — so the user can compare **+10 standard (5.00) ↔ +10 ascended (5.15)**.
- State lives in `useBuild` (`ascended` boolean, `canAscendNow`, `toggleAscend`). While
  ascended the enhancement slider floor is +10.

## UI structure (interactive view)

- **Hero**: rarity-framed icon · chips (type · rarity · ★stars · class · rank) · name.
  No KPI strip (removed to de-duplicate — rarity/tier/enh were echoed there).
- **`[ CONFIGURE ]` bar** (sticky on desktop): compact one-line controls —
  Enhancement slider (fuchsia ascension mark at +10), Breakthrough tier tabs, Reforge
  slider, and the `✦ Ascend` button. Each control shows its own value; no separate main
  readout (de-duplicated).
- **Module grid** (`[ TITLE ]` bracketed, 2-col): Main Stat / Possible Main Stats /
  Possible Substats / Effect (passive) / Singularity Ascension / Source / Recommended.
  Each value is a `FlashNum` (amber/fuchsia pulse on change).

`FlashNum` pulses on value change; accents are rarity hex, fuchsia for ascension, cyan
for buffs, amber for stat highlights (mirrors `globals.css`).

## Status / TODO

- **Done**: static Console view (prod), interactive preview behind `?build=live`, real
  main-stat formula (standard + ascended), choice-main selection with sub-pool exclusion,
  possible-substats display, multilingual passives/set-effects, explicit Ascend button
  with prereq gating.
- **Deferred**: **reforge → substat value** linkage (how reforge segments map onto the
  pool). Currently substats are shown as possible-value ranges only.
- **Not covered by data**: EE (no `item-stats-detail` entry) — live view uses the
  `eeStatRange` + curated effect fallback.
- **Rewire point**: when the progression data changes, only `buildSpec`/`buildModel` in
  `EquipmentDetailInteractive.tsx` and the formulas in `equipment-formula.ts` need edits.
  When `?build=live` graduates, promote `LIVE_LABELS` (inline LangMaps) to `messages.json`
  and decide whether to replace the static view.
